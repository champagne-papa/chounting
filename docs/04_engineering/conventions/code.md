# Code conventions

Naming, formatting, contribution rules, performance patterns, and
i18n discipline. Branch naming, commit conventions, and the rules
that govern how code is structured across the source tree.

See [`README.md`](./README.md) for the routing rule that determines
when a rule belongs here vs. another topical file.

---

## Contribution Conventions

- **Branch naming:** `feat/[ticket-id]-short-description`,
  `fix/[ticket-id]-description`
- **Phase branches:** `phase/N-short-description` (e.g.,
  `phase/1-storage-evidence-core`). Long-lived; merge at phase
  ratification with `--no-ff` to preserve arc topology. Existing
  phase branches (`worktree-phase-0-governance`, etc.) retain
  their current names — forward-applying convention only.
- **Conventional Commits:** `feat:`, `fix:`, `chore:`, `docs:`
- **New service function** →
  `src/services/[module]/[entity]Service.ts`
  - Per ADR-0020 (Decision item 6), pure deterministic logic
    that doesn't touch DB or I/O may be extracted into
    `src/core/[area]/` and called from the service. The
    service remains the entry point for cross-cutting concerns
    (transactions, audit, authorization). Extraction is
    opportunistic — when a service file is naturally edited
    and a pure-logic block is identified, that block can move.
    Pre-emptive extraction is not required.
- **New agent tool** → `src/agent/tools/[toolName].ts`
- **New Zod schema** →
  `src/shared/schemas/[module]/[entity].schema.ts`, then imported by
  service, route handler, and form component
- **Every PR:** updated Postman collection (if API changed), updated
  Zod schemas (if data shape changed), migration file (if schema
  changed)
- **Direct database calls outside `src/services/` are rejected at
  code review.** No exceptions, no urgency override
  (INV-SERVICE-001 enforcement).

## Performance Conventions

Source: PLAN.md §10 (performance rules that are painful to retrofit).

- **Bulk operations must be transactional.** All service functions
  that operate on multiple rows must accept arrays and execute a
  single transactional write. Never loop one at a time.
- **N+1 avoidance.** List endpoints (bills, transactions, ai_actions)
  must eager-load related rows (vendor name, account name, org name)
  in a single query using Postgres JOINs. Never loop.
- **No caching in Phases 1-2.** No Redis, no query caching. Defer
  entirely. Flag as Phase 3+ when report generation becomes slow.
- **Index plan check.** Every new service function query must be
  checked against the index plan in
  `docs/02_specs/data_model.md` before merging.

## i18n Conventions

Day 1 requirement, not an afterthought.

- **`next-intl`** for all UI strings.
- **URL structure:** `/[locale]/[orgId]/...` from day one. Both
  `[locale]` and `[orgId]` in the path (bookmarks, deep links,
  redirects all org-aware).
- **Translation files:** `messages/en.json`, `messages/fr-CA.json`,
  `messages/zh-Hant.json`. Phase 1.1 populates `en.json`; the other
  two exist with the same key structure but English fallback values.
- **Traditional Mandarin note:** `zh-Hant`, not `zh-TW`. The
  `next-intl` config uses `zh-Hant` as the key.
- **Placeholder locale fallback rule:** `fr-CA.json` and
  `zh-Hant.json` are generated by
  `cp en.json fr-CA.json && cp en.json zh-Hant.json` as a baseline.
  Real translations replace English values incrementally in later
  phases. **Every key in `en.json` must have a corresponding key in
  both other locale files, even if the value is still English.** Empty
  strings render as blank UI; missing keys throw at runtime in
  `next-intl` dev mode. Neither is acceptable.
- **Date and number formatting:** `Intl.DateTimeFormat`,
  `Intl.NumberFormat` with the user's locale. Never hardcode date or
  currency formatting.
- **Agent system prompts** include the user's `locale` and instruct
  Claude to return template IDs that have entries in all three locale
  files. The structured-response contract
  (`{template_id, params}` — not English prose) is specified in
  `docs/09_briefs/phase-1.2/agent_architecture.md`.

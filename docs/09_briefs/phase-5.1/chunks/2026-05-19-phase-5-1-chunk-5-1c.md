```typescript
async function loadBillsWithAmountDue(
  db: Db,
  org_id: string,
): Promise<BillWithAmountDue[]> {
  // Single query: bills + embedded bill_payment_allocations via PostgREST
  // nested-select. Eliminates the 2-query SELECT IN pattern that fired
  // Cat 2 URI-too-long against accumulated bill_payment_allocations row
  // state at Phase 6.5 chunk 6.2b (N=1) + Phase 5.1 chunk 5.1a (N=2) +
  // chunk 5.1b (N=3). Per scope-lock 2026-05-10 disposition: nested-
  // select IS a supabase-js JOIN-side aggregation pattern per PostgREST
  // embed semantics. See chunk 5.1c brief for fix-shape adjudication
  // (Fix A over Fix B batch / Fix C RPC) + Cat 2 N=3 graduation context.
  const { data: bills, error: billsErr } = await db
    .from('bills')
    .select(
      'bill_id, vendor_id, bill_number, due_date, amount_cad, lifecycle_state, bill_payment_allocations(amount_cad)',
    )
    .eq('org_id', org_id)
    .in('lifecycle_state', ['approved_for_payment', 'partially_paid']);
  if (billsErr) {
    throw new ServiceError(
      'READ_FAILED',
      `ap_report: bills+allocations lookup failed: ${billsErr.message}`,
    );
  }
  const billRows = (bills ?? []) as Array<{
    bill_id: string;
    vendor_id: string;
    bill_number: string | null;
    due_date: string | null;
    amount_cad: string | number;
    lifecycle_state: string;
    bill_payment_allocations: Array<{ amount_cad: string | number }>;
  }>;
  if (billRows.length === 0) {
    return [];
  }

  return billRows.map((b) => {
    const billAmount = toMoneyAmount(b.amount_cad);
    // Per-row aggregation over embedded allocations array. Empty array
    // (no allocations for this bill) → zeroMoney().
    const allocated = b.bill_payment_allocations.reduce(
      (acc, a) => addMoney(acc, toMoneyAmount(a.amount_cad)),
      zeroMoney(),
    );
    const amountDue = subtractMoney(billAmount, allocated);
    return {
      bill_id: b.bill_id,
      vendor_id: b.vendor_id,
      bill_number: b.bill_number,
      due_date: b.due_date,
      amount_cad: billAmount,
      amount_due: amountDue,
      lifecycle_state: b.lifecycle_state,
    };
  });
}
```

## 5. Operationalization

### 5.1 Fix-shape adjudication: Fix A (PostgREST nested-select)

Three approaches surfaced at brainstorming-side; brief-grade adjudication produces **Fix A** as the chunk 5.1c implementation.

**Fix A — PostgREST nested-select.** Replace 2-query pattern with one query using `.from('bills').select('..., bill_payment_allocations(amount_cad)')` syntax. JS-side aggregation moves to per-row reduction over embedded array.

Rationale chain:

1. **Scope-lock 2026-05-10 disposition alignment.** File header at apReportService.ts §13-16 ratifies "supabase-js JOIN-side aggregation; no Postgres RPCs; no new migrations." PostgREST nested-select IS a supabase-js JOIN-side aggregation pattern per PostgREST embed semantics (PostgREST translates the nested-select into a server-side JOIN against the FK relationship `bill_payment_allocations.bill_id REFERENCES bills.bill_id`). Fix A preserves the disposition explicitly.
2. **Single roundtrip per call.** Fix A reduces 2 DB roundtrips to 1, also improving call latency (small but measurable; not the load-bearing rationale but a positive side effect).
3. **No migration.** Fix A is a query-shape change only; no Layer 1 substrate changes; preserves the apReportService scope-lock disposition.
4. **SELECT IN URL pressure eliminated by construction.** The nested-select query URL contains the `.select(...)` string (~120 chars including embedded relation) + `.eq('org_id', org_id)` (~50 chars) + `.in('lifecycle_state', [...])` (~80 chars for 2 string literals). Total URL ~250 chars + URL encoding ~×1.5 = ~375 chars. Bounded by URL prefix + 3 simple filter clauses; does NOT scale with bill count.
5. **Behavior preservation by construction.** The nested-select returns each bill row with an embedded `bill_payment_allocations` array (FK relationship `bill_payment_allocations.bill_id REFERENCES bills.bill_id` enables the embed). Per-bill amount_due aggregation moves from index-then-loop (current) to per-row reduce (refactored); both produce the same `Map<bill_id, summedAllocations>` result. The `BillWithAmountDue[]` output interface is identical pre/post refactor.

Counter-evidence to Fix A surfaced at brief drafting (none load-bearing):

- **PostgREST nested-select row count limits.** PostgREST default `max-rows` setting is typically unlimited unless configured; nested-select payload is bounded by parent count × children-per-parent. At Session 23 onset: 254 open bills × 0 allocations each = 254 rows. At v1 production: expected ~hundreds to ~low-thousands of open bills per org × ~0-5 allocations each ≈ low-thousands of rows. Well within PostgREST defaults. **Verify at Session 24 impl-onset:** if `select * from settings where parameter='max-rows'` shows a configured limit < 10000, surface as Path C counter-evidence.
- **Embedded-array shape consumer-side handling.** Fix A returns `bill_payment_allocations: Array<{amount_cad}>` embedded per bill row. Helper internally aggregates via reduce; consumers receive the same `BillWithAmountDue[]` shape (interface preserved). **No consumer-side changes required** by construction.

**Fix B — Batch the SELECT IN.** Chunk billIds into batches (e.g., 100 per query); issue N SELECT IN queries; merge results. Brief-grade rejection: doesn't fundamentally fix the SELECT IN URL-length pattern (just delays the firing threshold); preserves 2-query pattern but multiplies query count; more invasive consumer pattern (forces helper to manage batch state); falls outside ~100-300 LOC band (likely closer to 200-400 LOC including batch-size constant + helper internal state). Aligned with scope-lock disposition but ergonomically inferior.

**Fix C — Database-side aggregation RPC.** New RPC function `get_bills_with_amount_due(p_org_id)` returns bills + computed amount_due via SQL aggregation. Brief-grade rejection: requires migration (departs from scope-lock 2026-05-10 disposition explicitly: "no Postgres RPCs; no new migrations"); breaks Phase 5.1 cycle scope discipline (no migrations at Phase 5.1 amendment cycle); shifts aggregation logic from JS (testable in isolation) to SQL (harder to unit-test). Cleanest pattern in pure DB terms but disposition-violating at the chunk-5.1c grain.

**Brief lean ratified: Fix A.** If Session 24 impl-onset surfaces counter-evidence (e.g., PostgREST nested-select payload size exceeds expected v1 limits at the 254-open-bill substrate scale), lean shifts via Path C reactive invocation to Fix B (preserve scope-lock disposition; deeper invasiveness) OR Fix C (depart from disposition; cleanest pattern). Brief assumes Fix A holds through impl-time per scope-lock disposition alignment.

## 8. Substrate touchpoint risks + mitigations

### Risk 1 — PostgREST nested-select payload size at v1 production scale

**Risk:** Fix A returns bills + embedded `bill_payment_allocations` array per bill row. If PostgREST `max-rows` setting is configured below the expected nested-select row count, the query is silently truncated and per-bill amount_due aggregation produces incorrect results.

**Mitigation:** Verify-from-disk at Session 24 impl-onset: query PostgREST settings via `select * from settings` (or equivalent supabase-cli command) to confirm `max-rows` is unlimited OR exceeds the expected v1 nested-select count (low-thousands of rows per org). If configured limit < expected, surface as Path C counter-evidence and shift fix-shape lean to Fix B (batch the SELECT IN; preserves scope-lock disposition) OR Fix C (RPC; departs from disposition; deeper change scope).

### Risk 2 — Behavior preservation across 4 consumer methods

**Risk:** Refactored helper returns `BillWithAmountDue[]` shape; consumers must observe identical aggregation semantics. If embedded-array iteration order differs from current index-then-loop aggregation order, money sum results MAY differ in edge cases (e.g., addMoney non-associativity at extreme precision boundaries — theoretical concern; not load-bearing at numeric(20,4) precision).

**Mitigation:** addMoney implementation at money.schema.ts uses decimal.js for exact arithmetic; addition is associative + commutative. Iteration order does NOT affect sum result at chunk 5.1c grain. Behavior preservation evidence at validation gate via Cat 2 6 → 0 transition + 3 integration test fixtures (apAging boundary thresholds + openBills filter exclusion + paymentApprovalQueue happy path) passing post-refactor.

### Risk 3 — activePayments has no direct service-grade integration test

**Mitigation:** Brief acknowledges this gap explicitly at §2.2. Full-suite vitest sweep at validation gate (a) provides indirect coverage.

## Goal

Ship the engine-agnostic OCR/extraction substrate per ADR-0011 §5 + §9 — three immutable tables (`ocr_runs`, `extraction_runs`, `document_artifacts`) with full constraint discipline + through-parent RLS + immutability triggers — as a single bundled commit.

**Phase-done bar refined to substrate-walkable** = admin-INSERT + constraint/trigger/RLS verification from tests. Chunk 4 ships no writer service; the Phase 7 Tier 2 pipeline orchestrator (per ADR-0014) owns the writer end-to-end. The friction-journal paragraph names the three deferred proofs (Pattern B service shape / audit-log RPC integration / Zod against real-caller payloads) explicitly so future-me doesn't silently absorb the gap.

**Walkable proof at chunk close**: an integration test admin-INSERTs the full chain (source_document → ocr_run → extraction_run → document_artifact), reads it back, Zod-parses the document_artifact row, asserts the supersession chain works on a second ocr_run, and confirms RLS through-parent rejects cross-org reads and writes. The substrate is exercisable end-to-end; the writer at Phase 7 will slot into the established shape.

### ADR-0010 three-layer reserved-enum discipline (chunk-4 application)

- **Layer 1 (DB CHECK)**: `engine IN ('paddleocr')`. Two reserved values (`tesseract`, `claude_vision_3_5`) stay in the ENUM type but CHECK-rejected. Future engine activation lands as a group when post-v1 engines ship.
- **Layer 2 (Zod)**: `DocumentArtifactEngineSchema` lists only `paddleocr`.
- **Layer 3 (service)**: N/A at chunk 4 — no service write path. Reserved for Phase 7.

Constraint name: `document_artifacts_engine_v1_active` (group-activation per chunk-3 precedent — `_v1_active` for "all post-v1 values activate together," `_chunk_N_active` for incremental broadening). Engine activates as a group when post-v1 engines ship.

### §5 column-shape preservation

`document_artifacts` is specified at ADR-0011 §5 lines 413-436 with 13 columns. The chunk-4 migration preserves the shape verbatim:

- `id`, `source_document_id` (FK), `ocr_run_id` (FK), `extraction_run_id` (FK).
- `engine` (ENUM — see ENUM-vs-text interpretation below), `engine_version` (text).
- `pages` / `lines` / `words` (jsonb), `quality_flags` (text[] — **not** jsonb per §5 line 429), `pipeline_trace` (jsonb).
- `confidence` (numeric, NULLable with range CHECK — see confidence-NULL semantics below), `created_at` (timestamptz).

**Notably absent: `created_by`.** §5 does not include a creator column. Chunks 1-3 all carry `created_by`; document_artifacts breaks that pattern by-§5-design. The reasoning: document_artifacts is always-pipeline-written; actor identity lives at the audit_log layer Phase 7 writes when invoking the pipeline. The migration comment names the asymmetry.

`ocr_runs` and `extraction_runs` are schema-deferred by ADR-0011 §3 ("the exact final shape of the set ... is owned by the Phase 1 / Phase 2 / Phase 3 / Phase 4 implementation plans, not by this ADR"). Chunk 4 ships minimum-viable shapes consistent with §9 Rules 1 and 2 (immutability + supersession + UNIQUE tuple). Both runs tables carry `created_by` — they're chunk-4-defined and follow chunks-1-3 convention.

### Engine ENUM vs §5's "text" framing

§5 line 418-421 specifies `engine` as `text`, "for example, paddleocr, tesseract, claude_vision_3_5." Chunk 4 ships as **ENUM**, not text, per ADR-0010 three-layer discipline + chunks 1-3 precedent. Interpretation:

- §5's "text" framing is non-binding spec language. §3 lines 938-944 explicitly delegates schema-shape choices to implementation plans.
- §5's "for example" engine list is non-exhaustive in a way §6 (document_type) and §13 (resolution_action) enums are not. The ENUM ship interprets §5's three-name list as closed.
- If Phase 7 needs a value §5 didn't enumerate, `ALTER TYPE` adds it. Cheap.

The migration comment names this interpretation so future-readers see the receipt.

### Confidence NULL semantics

§5 says `confidence numeric` with no NULL/default constraint. Chunk 4 ships `confidence numeric NULL` with `CHECK (confidence IS NULL OR (confidence >= 0 AND confidence <= 1))`.

Rationale: a row with no confidence written by Phase 7 (i.e., the writer forgot) is a Phase 7 bug. `NOT NULL DEFAULT 0` would conflate "Phase 7 wrote zero confidence" with "Phase 7 forgot to populate" — different semantic states, same byte. NULL preserves the distinction; ADR-0019 routing logic gets to decide what unknown-confidence routes to (almost certainly exception). `ALTER NOT NULL` when Phase 7 wires the writer with proven populate-discipline.

### ocr_runs uniqueness — by-design absent

`ocr_runs` carries `supersedes_ocr_run_id` per §9 Rule 1 but **no uniqueness constraint on `source_document_id`**. Supersession chains are by-design per §9 Rule 1 — re-extraction produces a new row that supersedes the prior, both rows preserved.

The "current head" pointer for ocr_runs (which row is the live one for this document) is owned by Phase 7 / ADR-0014 Q69. Don't add an `is_current` flag or a `(source_document_id, status='current')` partial unique index at chunk 4 — that's Phase 7's surface.

### RLS through-parent via source_documents.org_id

All three tables are org-scoped via FK to `source_documents.id`; `source_documents.org_id` is the true authority. RLS pattern per table is identical (mirrors chunk-3's EXISTS-subquery through `document_cases`, except chunk-4 goes through `source_documents`):

```sql
CREATE POLICY <table>_select ON <table>
  FOR SELECT USING (
    EXISTS (
      SELECT 1 FROM source_documents sd
      WHERE sd.id = <table>.source_document_id
        AND user_has_org_access(sd.org_id)
    )
  );

CREATE POLICY <table>_insert ON <table>
  FOR INSERT WITH CHECK (
    EXISTS (
      SELECT 1 FROM source_documents sd
      WHERE sd.id = <table>.source_document_id
        AND user_has_org_access(sd.org_id)
    )
  );

CREATE POLICY <table>_no_update ON <table>
  FOR UPDATE USING (false);

CREATE POLICY <table>_no_delete ON <table>
  FOR DELETE USING (false);
```

Belt-and-suspenders: UPDATE/DELETE blocked at RLS layer; immutability triggers below catch service_role bypass. Verified shape against chunk-3 migration at `20240145000000_document_case_sources.sql` lines 82-104.

### Immutability triggers — one function per table, two triggers per table

Per chunk-3 precedent. Each table gets a dedicated `reject_<table>_mutation()` trigger function + `trg_<table>_no_update` (BEFORE UPDATE) and `trg_<table>_no_delete` (BEFORE DELETE) triggers. Error messages name the table and the per-table carve-out rationale:

- `ocr_runs`: "re-extraction produces new rows per §9 Rule 1, not in-place updates"
- `extraction_runs`: "re-extraction against new ocr_runs produces new (source_document_id, ocr_run_id, extraction_version) rows per §9 Rule 2"
- `document_artifacts`: "replayability requires new rows referencing new ocr_run_id / extraction_run_id per §9 + §5"

TRUNCATE protection skipped per Option C asymmetry (workflow/substrate rows, not evidence anchors like `source_document_versions`).

### Substrate-walkable phase-done bar

Chunks 1-3 each shipped a service contract callable from at least one test exercising the real data path. Chunk 4 has no service. The phase-done bar is refined to **substrate-walkable** = admin-INSERT + constraint/trigger/RLS verification from tests. Three proofs chunks 1-3 landed are deferred to Phase 7's writer:

1. Pattern B unwrapped-export + ServiceError shape for this surface.
2. Audit-log RPC integration with parent-derived `org_id` (chunk-3 canonical pattern at `attach_document_case_source_with_audit`).
3. Zod boundary against real-caller payloads (vs admin-test fixtures).

The friction-journal paragraph names these three explicitly. Item 4 of the working discipline (phase-done means end-to-end-walkable) is preserved by naming the deferral, not by silently relaxing it.

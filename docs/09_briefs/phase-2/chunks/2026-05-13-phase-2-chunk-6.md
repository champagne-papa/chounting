# Phase 2 Chunk 6 — exception queue + `resolution_action` / `exception_status` / `exception_reason` enums + `documentExceptionService`

**Date**: 2026-05-13
**Phase**: 2 (Document Core)
**Chunk**: 6 of N

## Goal

Ship the exception-queue substrate (`exception_queue_entries` table + three closed enums) plus `documentExceptionService` (`enqueueException` + `resolveException` + `readExceptionQueueEntry`) per ADR-0011 §13, as a single bundled commit. The exception queue is "the bulk of v1's user-visible work" per §13's first-class-deliverable framing — chunk 6 owns the substrate + service surface; UI bulk operations and document-type-aware actions live in the UI layer.

**Phase-done bar returns to service-walkable** per chunks 1-3 + 5 precedent. Chunk 6 has natural service surface: `enqueueException` atomically creates a queue row + transitions the case to `needs_review`; `resolveException` atomically marks the queue row resolved + flips the case to a terminal state per the 9-action terminal-state mapping (5 → `proposed`, 3 → `rejected`, 1 → `classified` for `reprocess` via LEGAL_TRANSITIONS broadening). Effects deferred to consuming services per Option (a) — no Phase 5 service calls from chunk-6 resolve.

**Walkable proof at chunk close**: an integration test creates a `document_case` via `documentCaseService.createDocumentCase`, transitions it `received → classified` via `documentCaseService.transition` (chunk-2), calls `documentExceptionService.enqueueException(case_id, exception_reason='low_confidence_classification', ...)` to enqueue + atomically transition `classified → needs_review`, reads the queue entry back, then calls `documentExceptionService.resolveException(entry_id, resolution_action='reprocess', ...)` to resolve + atomically transition `needs_review → classified`. The full chain — chunk-1 case substrate × chunk-2 transition × chunk-6 queue + LEGAL_TRANSITIONS broadening — is exercisable end-to-end.

### ADR-0010 three-layer reserved-enum discipline (chunk-6 application across three enums)

All three layers ship at chunk 6, applied to three separate enums:

- **Layer 1 (DB CHECK)**: three CHECKs — `resolution_action_chunk_6_active` (9-value IN list, NULL-allowed), `exception_status_chunk_6_active` (2-value: `open`/`resolved`), `exception_reason_chunk_6_active` (6-value IN list).

### 9-action terminal-state mapping (highest-risk transcription surface)

`resolveException(input)` reads `input.resolution_action`, dispatches the per-action terminal-state for `document_case.state`. The mapping is load-bearing for the case-state ↔ exception-state coupling; one mis-mapped action produces one wrong test.

| `resolution_action` | terminal `document_case.state` | Notes |
|---|---|---|
| `attach_to_existing_bill` | `proposed` | Controller's choice IS an articulated proposal (attach this source_document to that bill). Future wiring creates the link as the materialized proposal. |
| `attach_to_existing_payment` | `proposed` | Same logic as attach_to_existing_bill. |
| `record_bill_payment` | `proposed` | Controller signals "record payment via Phase 5 form for the identified bill." Form commit produces the actual ProposedMutation. |
| `route_to_manual_entry` | `proposed` | Controller signals "manual entry via Phase 5 form for the document's type." Form commit produces ProposedMutation. |
| `manual_born_paid_workflow` | `proposed` | Controller signals "born-paid bundle workflow per ADR-0015 Scenario C." Form commit produces ProposedMutationBundle. |
| `mark_duplicate` | `rejected` | Case closed; duplicate distinction lives in `resolution_action` audit column. §3 `rejected → archived` automation eventually archives. |
| `mark_non_accounting` | `rejected` | Case closed; document-type distinction in `resolution_action`. Same cleanup path. |
| `archive` | `rejected` | Case closed; archive-vs-mark_duplicate-vs-mark_non_accounting distinction in `resolution_action`. No direct `needs_review → archived` transition needed. |
| `reprocess` | `classified` | Re-run extraction/router from a clean slate. **Requires LEGAL_TRANSITIONS broadening** — see next subsection. |

Summary: 5 → `proposed`, 3 → `rejected`, 1 → `classified`.

The three → `rejected` entries are semantically distinct via the `resolution_action` audit column, NOT collapsed. `resolution_action` is the resolution-semantics carrier; `lifecycle_state` is the case-state carrier.

### Direct org_id RLS (chunks 1-2 substrate-spine convention)

`exception_queue_entries` carries `org_id uuid NOT NULL` directly (FK to `organizations(org_id) ON DELETE RESTRICT`), mirroring chunk-1 `document_cases` substrate-spine pattern (verified at chunk-1 migration line 64 + RLS pattern lines 86-102). Direct org_id is cheaper at query time than chunks 3-5's through-parent EXISTS-subquery; §13's framing of the queue as "the bulk of v1's user-visible work" makes the cheaper RLS shape load-bearing for UX hot-path performance.

4-policy RLS mirrors chunk-1 verbatim:

```sql
CREATE POLICY exception_queue_entries_select ON exception_queue_entries
  FOR SELECT USING (user_has_org_access(org_id));
CREATE POLICY exception_queue_entries_insert ON exception_queue_entries
  FOR INSERT WITH CHECK (user_has_org_access(org_id));
CREATE POLICY exception_queue_entries_update ON exception_queue_entries
  FOR UPDATE USING (user_has_org_access(org_id))
  WITH CHECK (user_has_org_access(org_id));
CREATE POLICY exception_queue_entries_no_delete ON exception_queue_entries
  FOR DELETE USING (false);
```

The enqueue + resolve RPCs derive `org_id` from `document_cases.org_id` via subquery per chunks-3-5+ parent-derived-org_id-in-RPC pattern. `org_id` on the queue row is single-source-of-truth at INSERT time (the parent case's org_id at the moment of insertion); the service never passes org_id; the RPC never accepts org_id in `p_audit`.

FK ON DELETE clause: `exception_queue_entries.document_case_id REFERENCES document_cases(id) ON DELETE RESTRICT`. Verified-from-disk at brief-loop: chunk-1 ships `reject_document_cases_delete()` BEFORE DELETE trigger (chunk-1 migration lines 134-145), so `document_cases` rows never delete in practice — RESTRICT is appropriate because the trigger blocks any cascade attempt regardless. Phase 1 source_documents has parallel pattern at storage migration lines 413/422/424 (chunk-5 precedent).

### §6(a) + §6(b) two-mechanism on 5 mutable columns (vs chunk-5's 1)

Chunk-5 introduced the column-level GRANT + BEFORE UPDATE OF trigger composition for narrow service_role UPDATE on `source_document_links.link_status` (one column). Chunk 6 reuses the pattern on 5 mutable columns:

**§6(a) — column-level GRANT/REVOKE for service_role:**

```sql
REVOKE UPDATE ON exception_queue_entries FROM service_role;
GRANT UPDATE (exception_status, resolution_action, resolution_notes, resolved_at, resolved_by)
  ON exception_queue_entries TO service_role;
```

Service_role can UPDATE only the 5 resolution-cycle columns. Other columns (`exception_queue_entry_id`, `org_id`, `document_case_id`, `source_document_id`, `exception_reason`, `trace_id`, `created_at`, `created_by`) are immutable post-INSERT.

**§6(b) — BEFORE UPDATE OF `exception_status` trigger** for one-way transition CHECK:

```sql
CREATE OR REPLACE FUNCTION reject_invalid_exception_status_transition()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.exception_status = 'resolved' AND NEW.exception_status IS DISTINCT FROM 'resolved' THEN
    RAISE EXCEPTION 'exception_status is one-way: resolved cannot transition'
      USING ERRCODE = 'feature_not_supported';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_exception_queue_entries_status_transition
  BEFORE UPDATE OF exception_status ON exception_queue_entries
  FOR EACH ROW
  EXECUTE FUNCTION reject_invalid_exception_status_transition();
```

Column-list trigger (`BEFORE UPDATE OF exception_status`) narrows firing surface; trigger fires only on `exception_status` mutations. Layer 1 CHECK already restricts `exception_status` to `('open', 'resolved')` at chunk-6 active subset; the trigger adds the one-way directionality on top (open→resolved permitted; resolved→open or resolved→cancelled rejected).

Composition: GRANT enforces "which columns are mutable" (the 5 resolution-cycle columns); trigger enforces "valid transition on the one-way column" (no resolved→anything regression). No overlap; clean architecture. Migration top-comment names the composition explicitly per chunk-5 precedent.

### Partial UNIQUE on `(document_case_id) WHERE open` + N=4 test sequence

```sql
CREATE UNIQUE INDEX exception_queue_entries_open_per_case_idx
  ON exception_queue_entries (document_case_id)
  WHERE exception_status = 'open';
```

Partial unique index — at most one open exception per case at a time; multiple resolved historical rows preserved. Postgres index updates as rows update: when an exception flips to `resolved`, the index entry drops automatically, freeing the case_id for re-enqueue. Case-state ↔ exception-state 1:1 coupling while open: a case is in `needs_review` ↔ a case has exactly one open exception.

Duplicate-enqueue rejected with typed `ServiceError('EXCEPTION_ALREADY_OPEN', ...)` mapped from the Postgres `unique_violation` ERRCODE in the service layer. Chunk-5 `LINKED_ENTITY_NOT_FOUND` precedent: new ServiceError codes ship in lockstep with their first emitter. `EXCEPTION_ALREADY_OPEN` added to the union in `apps/web/src/services/errors/ServiceError.ts`.

**N=4 partial-index-under-state-transitions test sequence** (single test, 4 assertions; highest-risk shape for the partial-index semantics):

1. `enqueueException(case_X, reason_A)` → open exception created; assert success.
2. `enqueueException(case_X, reason_B)` → assert `EXCEPTION_ALREADY_OPEN` ServiceError.
3. `resolveException(entry_id_A, action='archive')` → status flips to `resolved`; partial-index entry drops.
4. `enqueueException(case_X, reason_B)` → assert success; case_X now has 1 historical resolved + 1 new open.

Catches naive full-UNIQUE bugs (would false-block step 4) AND naive partial-index bugs (would false-pass step 2).

### Two atomic RPCs (parent-derived org_id)

Per chunks 3-5+ canonical pattern, both RPCs derive `org_id` from `document_cases` via subquery at INSERT time. Service never passes `org_id`; `p_audit` carries `user_id`, `trace_id`, `action`, `entity_type`, `tool_name`, `reason`, `idempotency_key` per chunk-1/2 audit_log INSERT shape (verified at chunk-1 migration lines 174-190).

**`enqueue_exception_with_audit(p_entry jsonb, p_audit jsonb) RETURNS uuid`**:
- INSERT 1: `exception_queue_entries` with `org_id` derived from `document_cases.org_id` subquery.
- Atomic case transition: `UPDATE document_cases SET state = 'needs_review' WHERE id = v_case_id AND state IN ('classified', 'matched')`. If `state` is not in `classified`/`matched`, the UPDATE matches zero rows; raise `INVALID_TRANSITION` exception with `check_violation` ERRCODE.
- INSERT 2: `audit_log` with `entity_type='exception_queue_entry'`, `action='exception_enqueued'`, `entity_id=v_entry_id`, `after_state_id=v_entry_id`.
- Returns the new `exception_queue_entry_id`.

**`resolve_exception_with_audit(p_entry_id uuid, p_resolution jsonb, p_audit jsonb) RETURNS uuid`**:
- SELECT the queue row + parent case state FOR UPDATE (chunk-2 FOR UPDATE precedent serializes concurrent resolve attempts).
- Reject if `exception_status != 'open'` (Postgres trigger §6(b) is defense-in-depth).
- Compute terminal case state via per-action mapping (CASE expression: 5 actions → `proposed`, 3 → `rejected`, 1 → `classified`).
- UPDATE `exception_queue_entries`: `exception_status = 'resolved'`, `resolution_action = p_resolution.action`, `resolution_notes = p_resolution.notes`, `resolved_at = now()`, `resolved_by = p_resolution.resolved_by`.
- UPDATE `document_cases`: `state = v_terminal_state`. Layer 1 CHECK (`_chunk_6_active`) admits all 4 possible targets (`proposed`, `rejected`, `classified`, plus existing v1 states).
- INSERT `audit_log` with `entity_type='exception_queue_entry'`, `action='exception_resolved'`, `before_state=jsonb_build_object('exception_status', 'open', 'document_case_state', v_before_case_state)`, `after_state_id=p_entry_id`.
- Returns `p_entry_id`.

Both RPCs use `SECURITY INVOKER` (chunks 1-5 precedent — caller's permissions apply; RLS still enforces org-scope). `GRANT EXECUTE ON FUNCTION ... TO service_role` at end of each definition.

### `matched` vs `proposed` distinction is load-bearing

`matched` is the state for Router-identified candidates awaiting Router-driven proposal materialization (per §3: `matched → proposed` is automation, produces a ProposedMutation/Bundle/Attachment). `proposed` is the state for any articulated proposal — automation OR human-from-queue. The controller's resolution-action choice IS an articulated proposal (controller has named the target bill / payment / form path explicitly), so 5 of the 9 v1-active actions terminal at `proposed`, not `matched`. Routing through `matched` would (a) pretend the Router identified the candidate when it didn't, and (b) introduce a stuck-state risk (no automation exists at chunk-6 time to flip `matched → proposed` for human-resolved cases; Router re-evaluation fires on entity-state changes, not case-state changes).

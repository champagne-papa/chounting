**Per-document-type candidate generation pseudocode extensions at `documentRouterService.completeCandidate` (Subsystem 1 surface):**

Extend the candidate generation logic across the three v1-active document types (`vendor_invoice` + `receipt` + `payment_confirmation`) per ADR-0018 §2 lines 364-449 pseudocode-level specification of candidate generation. Per-document-type narrative covers:

**(a) `vendor_invoice` → bill matching** per ADR-0018 §2 lines 367-394:

- **Scenario A inferred-target (common path):** `invoice-arrives-no-bill-yet`. Subsystem 1 emits candidate with `linked_entity_type = 'bill'` + `linked_entity_id` null (bill-about-to-be-created). The inferred-target shape is the canonical first-emission path at v1 — invoices arrive at OCR pipeline before bill records are manually created in most operational sequences. Per-feature scoring narrative: vendor match (vendor_id from Subsystem 1 inputs vs candidate bill vendor_id) + amount match (invoice total vs candidate bill total_amount) + date proximity (invoice date vs candidate bill issue_date) + bill_number/invoice_number alignment (invoice_number from extracted features vs candidate bill bill_number).
- **Scenario B existing-bill matching:** `invoice-arrives-bill-manually-entered-without-evidence`. Subsystem 1 emits candidate with `linked_entity_type = 'bill'` + `linked_entity_id = <existing bill UUID>`. The existing-bill matching shape covers operational sequences where bills were created in-system before the invoice arrived (e.g., recurring vendor bills entered from prior periods; vendor-confirmed bill amounts entered before invoice receipt). Per-feature scoring same axes as Scenario A; existing bill candidates surfaced via vendor + amount + date proximity query at `completeCandidate` read boundary (Tier 2.5 read per ADR-0018 §5).
- **Cross-scenario emission shape:** both Scenario A + Scenario B may emit candidates at single `completeCandidate` invocation per `vendor_invoice` document_type (N≥0 Scenario A candidates + N≥0 Scenario B candidates). The Subsystem 2 (resolveCandidates) ambiguity-margin-zero discipline filters at consumer surface per Phase 4 chunk 2 substrate.

**(b) `receipt` → payment matching** per ADR-0015 §7 three sub-scenarios + Scenario C exception routing:

- **Scenario A `(payment, payment_evidence)` attach to recorded payment:** receipt-as-evidence-pair-to-existing-payment. Subsystem 1 emits candidate with `linked_entity_type = 'payment'` + `linked_entity_id = <existing payment UUID>`. The canonical attach shape — recorded payments evidenced by receipts post-hoc (e.g., receipt arrives after wire-confirmation already recorded payment).
- **Scenario A variant `(payment, receipt)` receipt-as-primary:** Subsystem 1 emits candidate with `linked_entity_type = 'payment'` + `linked_entity_id` null (payment-about-to-be-created from receipt-as-primary). Per ADR-0015 §7 variant disambiguation framing. The receipt-as-primary shape covers receipts arriving as the originating payment evidence (e.g., cash payment evidenced only by receipt at receipt-arrival time).
- **Scenario B `(bill, receipt)` triggers bill payment:** Subsystem 1 emits candidate with `linked_entity_type = 'bill'` + `linked_entity_id = <existing bill UUID>` (receipt evidences bill payment about to be recorded; downstream dispatchTrigger T-series fires recordPayment). The bill-payment-trigger shape couples receipt-as-payment-evidence to existing bill; payment record creation fires at Subsystem 3 dispatchTrigger T-series per Phase 4 chunk 3 substrate.
- **Scenario C exception queue routing:** when N=0 high-confidence candidates surface at Subsystem 1 + `manualBornPaidBundleEntry` payload subtype applies, Subsystem 1 emits exception_queue routing signal via Subsystem 2 (Phase 4 chunk 2 substrate) with `resolution_action = route_to_manual_entry` per ADR-0011 §13. The manual-born-paid-bundle shape covers receipts where insufficient match evidence surfaces at Subsystem 1 grade; manual reconciliation at exception_queue surfaces as fallback per ADR-0015 §7.

Per-feature scoring narrative for receipt candidates: vendor match + amount match + date proximity + `authorization_reference` (extracted from receipt OCR; e.g., card authorization code or transaction reference number) + `payment_method` consistency (cash/check/card consistency vs existing payment `payment_method`).

**Receipt multi-scenario emission disambiguation:** Subsystem 1 may emit candidates from multiple scenarios at single `completeCandidate` invocation per receipt document_type. Subsystem 2 (resolveCandidates) ambiguity-margin-zero discipline filters at consumer surface; Subsystem 3 (dispatchTrigger) T-series dispatch fires the resolved candidate's downstream service call per ADR-0018 §item 3 dispatcher decomposition.

**(c) `payment_confirmation` → payment matching** per ADR-0018 §2 lines 442-449:

STEP 2: FIX DESIGN

Four candidate fix shapes:

(a) **Anchor on the Promoted-from line.** Stage A greps for the tag
    only on lines matching the Promoted-from pattern. Tight; misses
    any codification that doesn't use exact Promoted-from formatting.

(b) **Anchor on the Origin footer block.** Stage A greps for the tag
    within an Origin footer's text span (between the footer's start
    marker and the next section break). Looser; tolerates footer
    format variants.

(c) **Discriminator: tag NOT in cross-reference body.** Stage A finds
    all tag hits, then excludes any that appear within a Cross-
    references section's body. Inverse of (a)/(b); tolerates any
    footer format but requires recognizing cross-reference sections.

(d) **Structured metadata block.** A breaking change: require every
    convention to carry a small machine-readable metadata block
    (e.g., YAML frontmatter) declaring Promoted-from tags. Stage A
    parses the block rather than greppng prose. Highest precision;
    requires retrofit of existing conventions.

Each shape has tradeoffs. The audit's findings determine which is
right.

Specifically:

  - If audit shows footer format is consistent: (a) or (b) are
    cleanest. (a) is tighter; (b) is more tolerant.
  - If audit shows footer format varies: (c) may be the more
    tolerant approach, or (a)/(b) require normalizing the formats
    first.
  - If audit shows tag-in-prose mentions that pre-date the prose
    convention: (c) needs special handling for these legacy
    mentions, or they need to be migrated to file-path references.
  - If audit shows many false-positives across many tags: the
    operational cost of any fix is high; investing in (d)'s precision
    may be worth the retrofit cost.

Recommend one fix shape based on the audit. Wait for my approval
before applying.

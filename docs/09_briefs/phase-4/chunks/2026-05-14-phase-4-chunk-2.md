### ADR-0018 §item 3 owns Subsystem 2 contract; chunk 2 implements the envelope-less v1 shape

Per ADR-0018 §item 3 Decision-section, Subsystem 2 takes the candidate set produced by Subsystem 1 and routes it to one of three branches: (a) single winner — set head pointer + state transition; (b) ambiguous — propose multiple candidates to reconciliation UI; (c) no match — route to exception queue. Branch (b) presupposes Tier-1 ProposedEntryCard disambiguation UI for operator review + selection.

v1 ships without envelopes (`ProposedMutation`/`ProposedAttachment` TS types have zero codebase references at scope-lock 2026-05-13) and without the ProposedEntryCard UI. Chunk 2 implements an envelope-less v1 shape that collapses branch (b) → branch (c) at the substrate-mutation level (head pointer unset; case → `needs_review`; exception queue entry created via chunk-6 enqueueException) while preserving the branch identifier in the audit trail. When envelopes ship at the first Phase 5 reviewer / Phase 7 envelope chunk, an ADR-0018 §item 3 amendment ratifies (or corrects) the v1 collapse — likely either promoting branch (b) to emit an envelope with multiple candidate targets per §item 3's original framing, or ratifying chunk-2's collapse as canonical v1+ shape. Retrospective inventory item 6 stages this amendment.

The collapse is structurally a feature, not a workaround: under chunk-1's single-feature scoring (`confidence_score = vendor_match.confidence` for every candidate), the ambiguity margin (top − runner-up) is always 0 for N≥2 cases. There is no winner-selection signal that could populate a multi-candidate envelope informatively at v1; routing every ambiguous case to operator review is the operationally-honest behavior. F-J-α codifies the v1-operational-honesty framing.

### Three branches at substrate-mutation level

Subsystem 2's three branches map to three distinct substrate-mutation patterns. The branch decision is a pure function of (N, margin):

| Condition | Branch | Head pointer | State transition | Exception queue | exception_reason |
|---|---|---|---|---|---|
| N=0 | c | unset | classified → needs_review (via chunk-6) | enqueued | `'unmatched_router_candidate'` |
| N=1 | a | sole candidate | classified → matched | — | — |
| N≥2, margin ≥ threshold | a | top candidate (ORDER BY confidence_score DESC, id ASC) | classified → matched | — | — |
| N≥2, margin < threshold | b | unset | classified → needs_review (via chunk-6) | enqueued | `'multi_candidate_ambiguity'` |

Tiebreak `ORDER BY confidence_score DESC, id ASC` is preserved in service code (loadCandidatesForCase's ORDER BY) + decision-record before_state's `candidate_set_ids` ordering. At v1, branch (a) via the margin filter (N≥2 + differential scores) is structurally unreachable — every N≥2 case routes through branch (b) due to chunk-1 single-feature scoring (see "AMBIGUITY_MARGIN_V1_PROVISIONAL + chunk-1 single-feature scoring observation" below). F-J-α documents this v1-operational truth.

`AMBIGUITY_MARGIN_V1_PROVISIONAL = 0.05` constant ships at the top of `documentRouterService.ts` immediately below `CONFIDENCE_THRESHOLDS_V1_PROVISIONAL`. Value selection at chunks-2-ship is provisional (small-but-non-zero placeholder); ADR-0019 first calibration cycle (v1_ship_at + 6 months per ADR-0019 §3) ratifies. The constant's location at the consuming-service top makes the amendment surface mechanical.

### Branch (a) atomic RPC — `set_case_head_pointer_with_audit`

Branch (a) writes head pointer + state transition + emits two audit rows in a single transaction:

```sql
CREATE OR REPLACE FUNCTION set_case_head_pointer_with_audit(
  p_decision       JSONB,  -- { case_id, winner_candidate_id, trace_id }
  p_audit_decision JSONB,  -- decision-record audit payload (caller-constructed 10-field before_state)
  p_audit_mutation JSONB   -- state+head-pointer mutation audit payload (RPC constructs before_state)
) RETURNS UUID AS $$
DECLARE
  v_case_id             UUID := (p_decision->>'case_id')::uuid;
  v_winner_candidate_id UUID := (p_decision->>'winner_candidate_id')::uuid;
  v_before_state        document_case_state;
  v_before_head_pointer UUID;
BEGIN
  -- Capture prior state + prior head pointer for the mutation audit row.
  -- FOR UPDATE locks the row to serialize concurrent Subsystem 2
  -- invocations on the same case_id (mirrors chunk-2-Phase-2's
  -- update_document_case_state_with_audit pattern).
  SELECT state, current_relationship_candidate_id
    INTO v_before_state, v_before_head_pointer
  FROM document_cases
  WHERE id = v_case_id
  FOR UPDATE;

  IF v_before_state IS NULL THEN
    RAISE EXCEPTION 'document_case % not found', v_case_id
      USING ERRCODE = 'no_data_found';
  END IF;

  -- State-transition guard (G1): atomic UPDATE with WHERE state='classified'.
  -- If state has drifted (e.g., already 'matched' from a concurrent call,
  -- or 'needs_review' from a Subsystem 3 re-routing), the UPDATE matches
  -- zero rows. RAISE check_violation maps to INVALID_TRANSITION at the
  -- service boundary. Mirrors chunk-6's enqueue RPC guard pattern.
  UPDATE document_cases
  SET state = 'matched',
      current_relationship_candidate_id = v_winner_candidate_id
  WHERE id = v_case_id AND state = 'classified';

  IF NOT FOUND THEN
    RAISE EXCEPTION 'document_case % not in state classified', v_case_id
      USING ERRCODE = 'check_violation';
  END IF;

  -- Row 1: decision-record audit (caller-constructed 10-field before_state).
  INSERT INTO audit_log (
    org_id, user_id, trace_id, action, entity_type, entity_id,
    before_state, after_state_id, tool_name, idempotency_key, reason
  )
  VALUES (
    NULLIF(p_audit_decision->>'org_id', '')::uuid,
    NULLIF(p_audit_decision->>'user_id', '')::uuid,
    (p_audit_decision->>'trace_id')::uuid,
    p_audit_decision->>'action',           -- 'router_decision_recorded'
    p_audit_decision->>'entity_type',      -- 'document_case'
    v_case_id,
    p_audit_decision->'before_state',      -- DecisionRecordBeforeState 10-field JSONB
    v_case_id,
    p_audit_decision->>'tool_name',
    NULLIF(p_audit_decision->>'idempotency_key', '')::uuid,
    p_audit_decision->>'reason'
  );

  -- Row 2: state+head-pointer mutation audit (RPC-constructed 2-field before_state).
  INSERT INTO audit_log (
    org_id, user_id, trace_id, action, entity_type, entity_id,
    before_state, after_state_id, tool_name, idempotency_key, reason
  )
  VALUES (
    NULLIF(p_audit_mutation->>'org_id', '')::uuid,
    NULLIF(p_audit_mutation->>'user_id', '')::uuid,
    (p_audit_mutation->>'trace_id')::uuid,
    p_audit_mutation->>'action',           -- 'document_case_transitioned'
    p_audit_mutation->>'entity_type',      -- 'document_case'
    v_case_id,
    jsonb_build_object(
      'state', v_before_state::text,
      'current_relationship_candidate_id', v_before_head_pointer
    ),
    v_case_id,
    p_audit_mutation->>'tool_name',
    NULLIF(p_audit_mutation->>'idempotency_key', '')::uuid,
    p_audit_mutation->>'reason'
  );

  RETURN v_case_id;
END;
$$ LANGUAGE plpgsql SECURITY INVOKER;

GRANT EXECUTE ON FUNCTION set_case_head_pointer_with_audit(JSONB, JSONB, JSONB) TO service_role;
```

State-transition guard (G1): `UPDATE ... WHERE id=$1 AND state='classified' / IF NOT FOUND RAISE check_violation`. Service maps PostgreSQL error code 23514 → `INVALID_TRANSITION` ServiceError. Chunk-6 enqueue RPC precedent. NOT a Layer-1 CHECK constraint on `document_cases.state` — CHECK constraints can't express conditional state transitions; chunk-2-Phase-2's matrix-legality logic lives in `documentCaseService.transition`'s Layer 3a service code, and chunk-2-Phase-4's branch (a) guard lives in the atomic RPC.

### Branches (b)/(c) pure-audit RPC — `record_router_decision`

```sql
CREATE OR REPLACE FUNCTION record_router_decision(
  p_decision JSONB,
  p_audit    JSONB
) RETURNS UUID AS $$
DECLARE
  v_case_id  UUID := (p_decision->>'case_id')::uuid;
  v_audit_id UUID;
BEGIN
  -- Pure-audit emission. No substrate mutation at this RPC level —
  -- state transition (classified → needs_review) is owned by the
  -- subsequent cross-service call to documentExceptionService.enqueueException
  -- which composes enqueue_exception_with_audit.
  INSERT INTO audit_log (
    org_id, user_id, trace_id, action, entity_type, entity_id,
    before_state, after_state_id, tool_name, idempotency_key, reason
  )
  VALUES (
    NULLIF(p_audit->>'org_id', '')::uuid,
    NULLIF(p_audit->>'user_id', '')::uuid,
    (p_audit->>'trace_id')::uuid,
    p_audit->>'action',                -- 'router_decision_recorded'
    p_audit->>'entity_type',           -- 'document_case'
    v_case_id,
    p_audit->'before_state',           -- DecisionRecordBeforeState 10-field JSONB
    v_case_id,
    p_audit->>'tool_name',
    NULLIF(p_audit->>'idempotency_key', '')::uuid,
    p_audit->>'reason'
  )
  RETURNING audit_log_id INTO v_audit_id;

  RETURN v_audit_id;
END;
$$ LANGUAGE plpgsql SECURITY INVOKER;

GRANT EXECUTE ON FUNCTION record_router_decision(JSONB, JSONB) TO service_role;
```

The `_with_audit` suffix is deliberately dropped: this RPC has no substrate-mutation half. The audit IS the operation. F-J-ε codifies the discriminator. Note: branches (b)/(c) produce two audit rows total per invocation — one from this RPC (decision-record) + one from chunk-6's `enqueue_exception_with_audit` (exception enqueue + state transition). Branch (a) also produces two audit rows but from one atomic RPC.

`RETURNING audit_log_id` returns the just-emitted decision-record audit row's PK (the canonical column name on `audit_log` per the initial-schema DDL at `20240101000000_initial_schema.sql:485`). The return value is useful for service-side observability (e.g., `log.info({decision_record_audit_log_id: id, ...})`) — not currently threaded through the cross-service `enqueueException` call (chunk-6's `EnqueueExceptionInputSchema` doesn't accept an audit-row-id field at v1).

### Split `p_audit` params — structurally-distinct audit rows

Branch (a) atomic RPC takes `p_audit_decision` + `p_audit_mutation` as separate JSONB params because the two audit rows have structurally-distinct `before_state` shapes:

- **Row 1 (decision-record)** — 10-field `DecisionRecordBeforeState` JSONB constructed by the service (caller-side) and passed verbatim via `p_audit_decision.before_state`. The 10 fields include candidate set IDs, confidence scores, derived top/runner-up values, computed margin, at-decision-time threshold, branch identifier, winner candidate ID (if branch a), exception_reason (if branch b/c), and document_type. Service-side construction is necessary because most of these fields aren't in the substrate the RPC can read (e.g., `branch` is computed at decision time; `ambiguity_margin_threshold` is the at-decision-time `AMBIGUITY_MARGIN_V1_PROVISIONAL` value).
- **Row 2 (mutation)** — 2-field `{state, current_relationship_candidate_id}` JSONB constructed by the RPC body. The RPC reads prior state + prior head pointer via the `SELECT … FOR UPDATE` capture and builds the `before_state` JSONB itself (mirrors chunk-2-Phase-2's `update_document_case_state_with_audit` pattern). `p_audit_mutation` carries metadata only (action, entity_type, tool_name, etc.) — no `before_state` field.

This is the first instance at chunks 1-6 of two-structurally-distinct-audit-rows-per-RPC. Chunk-1-Phase-4's batch RPC `create_candidates_with_audit` emits N×1 rows (N candidates, structurally identical) — partial precedent for multi-row emission but rows share shape, so single `p_audit` remained adequate. F-J-δ codifies the discriminator: single-p_audit when rows are structurally identical (batch RPC N×1 pattern); split-p_audit when structurally distinct.

Five reasons for the split:
1. **Action-verb visibility**: TS-only closed vocabulary (`'router_decision_recorded'`, `'document_case_transitioned'`) belongs in TS code, not plpgsql literals. Hardcoding the verbs in the RPC body creates TS/SQL duality that the split avoids.
2. **Caller owns DecisionRecordBeforeState construction**: 10 fields, most of which the RPC can't reconstruct (margin, threshold, branch). Pushing construction to the service makes the responsibility split clean.
3. **Subsystem 3 forward-compat**: ADR-0016 §6 + ADR-0018 §Schema-deltas anticipate multi-RPC orchestration (e.g., `supersede_case_head_pointer_with_audit` writing a new candidate row + replacing the head pointer + emitting decision-record/state-transition/supersession audit rows). Split-p_audit at this signature extends to higher cardinalities.
4. **Query simplification**: Distinct payload shapes prevent ambiguity in audit-log queries that filter on `before_state->>'…'`. Each row's before_state has a stable, structure-known shape.
5. **Brief clarity**: Explicit per-row params make the RPC's contract self-documenting; reviewers don't parse a single overloaded `p_audit` to understand row cardinality.

### Pure-audit RPC suffix-drop discriminator (RPC-name-family discipline)

Chunk 2 establishes two RPC-name patterns:

- **Mutation RPC with `_with_audit` suffix**: `set_case_head_pointer_with_audit`. The suffix indicates: substrate mutation (head pointer + state transition) + co-emission of audit rows in single transaction. This establishes the Router-subsystem head-pointer-mutation verb family; future Subsystem 3 RPCs extend mechanically (e.g., `supersede_case_head_pointer_with_audit` for candidate replacement at chunks 3+).
- **Pure-audit RPC without suffix**: `record_router_decision`. The audit IS the operation; no substrate mutation at this RPC. The `_with_audit` suffix would be degenerate (the RPC does nothing but record); dropping it clarifies the RPC's purpose.

Discriminator: mutation-with-audit-co-emission keeps the `_with_audit` suffix (set_*_with_audit, update_*_with_audit, insert_*_with_audit, delete_*_with_audit); pure-audit-only drops the suffix (record_*, emit_*, log_*). Chunks 5-6 RPCs are all mutation-RPCs (`create_source_document_link_with_audit`, `enqueue_exception_with_audit`, `resolve_exception_with_audit`) so the pattern wasn't visible until chunk 2. F-J-ε codifies.

### Audit-row action verb — single-verb continuity from chunk-2-Phase-2

Chunk-2-Phase-2's transition RPC uses a single action verb `'document_case_transitioned'` for ALL state transitions, with source/target state captured in `before_state` JSONB. (`documentCaseService.ts:202` passes `action: 'document_case_transitioned'` for every transition; `update_document_case_state_with_audit` is agnostic to source/target.) Chunk-2-Phase-4's branch (a) row-2 (mutation) inherits this verb verbatim — `'document_case_transitioned'` — for convention continuity. Pre-flight #1 ratified outcome (b) single-verb against scope-lock R4.3 provisional `'document_case_matched'` (per-transition-specific outcome a).

**Two-axis verb-family disambiguation** (F-J-ε second axis): the **RPC-name family** is `set_case_head_pointer_*` (Subsystem 2's RPC + future Subsystem 3 `supersede_case_head_pointer_with_audit`); the **audit-row action verb** is `'document_case_transitioned'` (inherited from chunk-2-Phase-2 for state transitions; same verb across Phase-2 and Phase-4 callers, with the specific source/target preserved in before_state JSONB). The two families operate on independent axes — RPC names encode mutation-shape kinship; audit verbs encode case-state-machine events.

Decision-record audit row uses a chunk-2-Phase-4-specific action verb `'router_decision_recorded'` (R4.2 lock). Branch-agnostic; matches the decision-record semantic; forward-compat with the Phase 7 pipeline_trace `'router_ambiguity_resolution'` stage. This is a single-verb-per-event addition to the audit_log action vocabulary, not a verb-family proliferation.

### DecisionRecordBeforeState — forensic-payload self-containment

The decision-record audit row's `before_state` JSONB carries the full decision-input snapshot:

```typescript
type DecisionRecordBeforeState = {
  branch: 'a' | 'b' | 'c';
  candidate_set_ids: string[];                    // ordered: confidence_score DESC, id ASC
  confidence_scores: Record<string, number>;      // keyed by candidate_id
  top_confidence: number | null;                  // null iff N=0
  runner_up_confidence: number | null;            // null iff N<2
  ambiguity_margin_computed: number | null;       // null iff N<2; derived: top - runner_up
  ambiguity_margin_threshold: number;             // at-decision-time AMBIGUITY_MARGIN_V1_PROVISIONAL
  winner_candidate_id: string | null;             // non-null iff branch === 'a'
  exception_reason: ExceptionReason | null;       // non-null iff branch !== 'a'
  document_type: DocumentType;                    // calibration-cycle stratification key
};
```

### TS-side idempotency_key recipe — first-instance population

Pre-flight #2: chunks-5-6 service code does NOT populate `idempotency_key` (passes nothing in `p_audit`; RPCs use `NULLIF(p_audit->>'idempotency_key', '')::uuid` pass-through accepting null). `audit_log.idempotency_key` has NO UNIQUE constraint (verified at chunks-1-6 migrations + initial schema). Phase 1 precedent (`journalEntryService.ts:188`) is caller-supplied-or-null. **Chunk-2-Phase-4 is the first chunk at chunks-1-6 to populate `idempotency_key` deliberately.**

TS-side construction in the service:

```typescript
import { createHash } from 'node:crypto';

function deriveDecisionIdempotencyKey(case_id: string, trace_id: string): string {
  const hex = createHash('md5')
    .update(`${case_id}:${trace_id}:router_decision_recorded`)
    .digest('hex');
  return `${hex.slice(0,8)}-${hex.slice(8,12)}-${hex.slice(12,16)}-${hex.slice(16,20)}-${hex.slice(20)}`;
}
```

Components: `(case_id, trace_id, 'router_decision_recorded')`. The action verb (R4.2 lock) is included as a discriminator so a single trace_id with multiple Router decisions (e.g., Subsystem 3 re-evaluation reusing the trace_id) doesn't collide on idempotency_key. Recipe is forensic-correlation-not-uniqueness: no UNIQUE constraint exists; retries produce multiple decision-record rows under the same idempotency_key; querying `GROUP BY idempotency_key` deduplicates at higher orchestration layers. Tier 2.5 pipeline orchestrator's per-case serialization makes practical concurrency low at v1.

TS-side over SQL-side because (a) the service has all components naturally (case_id from input, trace_id from ctx, action-verb literal at the service site); (b) the deterministic recipe is visible at the service call-site where F-J-β codifies the new pattern; (c) the service can re-derive the key for forensic-replay queries without round-tripping; (d) keeps RPCs simpler (pure data-write, no derived-value construction). RPC's existing `NULLIF(p_audit_decision->>'idempotency_key', '')::uuid` pattern (chunks-5-6 precedent) carries the value through.

**Cross-row asymmetry**: under the same trace_id, chunk-2-Phase-4's decision-record row carries a populated idempotency_key; chunk-6's enqueueException audit row (emitted for branches b/c) leaves idempotency_key null because chunk-6's service doesn't construct one (unchanged at chunk-2 ship). The asymmetry is intentional — trace_id remains the canonical correlation key; idempotency_key is decision-record-specific forensic-correlation. F-J-β documents the asymmetry + discriminator rule.

F-J-β framing: first-instance establishment of populated idempotency_key with forensic-correlation intent. Discriminator for future chunks: populate deterministic key when the row needs retry-correlation as a queryable forensic axis; leave null when trace_id alone suffices.

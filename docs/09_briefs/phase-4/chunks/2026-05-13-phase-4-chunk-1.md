### ADR-0018 §item 2 owns Subsystem 1 contract; chunk 1 invents the DDL

Per ADR-0018 §item 2 Decision-section + Outputs subsection, Subsystem 1's contract is: given ADR-0014's "incomplete candidate" (structural classification + extracted fields + vendor match + `requiresTransactionalLookup` flag), read committed AP/Spend state, produce zero or more completed `DocumentRelationshipCandidate` rows with `(linked_entity_type, linked_entity_id, link_role, confidence_score, candidate_features)`. ADR-0011 §9 rule 3 specifies the versioning mechanic (`supersedes_candidate_id` self-FK; re-evaluation produces new rows referencing prior).

ADR-0018 + ADR-0011 are silent on the candidate-table column shape beyond these five output fields + versioning; chunk 1 invents the full 13-column DDL. Verified-from-disk at scope-lock 2026-05-13: zero codebase references to `document_relationship_candidates`, `DocumentRelationshipCandidate`, `documentRouterService`, `completeCandidate`, `re_routing_trigger`, `IncompleteCandidate`, or `requiresTransactionalLookup` (greenfield).

### Immutable-spine RLS shape composition (first-instance at chunk 1)

Chunk-1 introduces a composition not seen in chunks 1-6: chunk-6's direct-org_id 4-policy RLS + chunks-1-2's REVOKE-without-GRANT immutability defense + no column-immutability trigger + RLS UPDATE/DELETE `USING (false)`. The composition fits because `document_relationship_candidates` is first-class spine (own lifecycle via versioning) AND fully immutable post-insert (no mutable workflow columns; supersession is INSERT-of-new-row, not UPDATE).

Three-layer defense:

1. **`REVOKE UPDATE, DELETE ON document_relationship_candidates FROM service_role`** — service_role privilege removed entirely. NO column-level GRANT (degenerate — no mutable columns to grant access to). Diverges from chunks-5-6 which REVOKE + GRANT narrowly on mutable resolution-cycle columns.
2. **RLS UPDATE `USING (false)` + DELETE `USING (false)`** — covers authenticator/authenticated user-role clients (which don't have service_role privilege but could hit the table via user JWT through PostgREST). Belt-and-suspenders defense beyond the service_role REVOKE.
3. **No `updateCandidate()` / `deleteCandidate()` method at service layer** — the service surface has no mutation method other than INSERT (via `completeCandidate`'s atomic RPC). Subsystem 3 re-evaluation (chunks 2+) creates new rows via `supersedes_candidate_id`, never UPDATEs prior rows.

NO column-immutability trigger ships. Chunk-1's `document_cases` substrate uses such a trigger because its workflow columns ARE mutable (`state`, `current_relationship_candidate_id`, `classification_confidence`); the trigger protects audit-anchor columns while permitting workflow updates. `document_relationship_candidates` has no mutable columns at all, so the trigger would be cargo-cult (REVOKE + RLS already cover everything).

Migration top-comment names the composition explicitly so future-me auditing chunk-1 finds the "why this defense shape" answer in code, not just in the scope-lock memory file.

### 4-policy direct-org_id RLS (chunks-1-2 + chunk-6 substrate-spine convention)

`document_relationship_candidates.org_id uuid NOT NULL REFERENCES organizations(org_id) ON DELETE RESTRICT`. Direct org_id mirrors chunk-6 `exception_queue_entries` substrate-spine pattern (chunk-6 migration lines 74-79 verbatim reasoning: "spine entity (operational unit with own lifecycle), not a join-child; direct org_id is cheaper at query time than EXISTS-subquery"). Chunk-1 of Phase 4 fits the same discriminator: first-class identity (referenced via `document_cases.current_relationship_candidate_id` head pointer when Subsystem 2 ships); own lifecycle (created/superseded via FK chain); aggregate query volume across cases (Subsystem 3 cross-case dispatcher when chunks 2+).

4-policy shape:

```sql
ALTER TABLE document_relationship_candidates ENABLE ROW LEVEL SECURITY;

CREATE POLICY document_relationship_candidates_select
  FOR SELECT USING (user_has_org_access(org_id));
CREATE POLICY document_relationship_candidates_insert
  FOR INSERT WITH CHECK (user_has_org_access(org_id));
CREATE POLICY document_relationship_candidates_no_update
  FOR UPDATE USING (false);
CREATE POLICY document_relationship_candidates_no_delete
  FOR DELETE USING (false);
```

org_id is parent-derived in the atomic RPC via subquery from `document_cases.org_id` per chunks 3+ canonical pattern (chunk-6 migration line 343: "single source of truth at INSERT time"). The candidate row carries `org_id` directly for cheap RLS evaluation; the value is computed-not-passed at INSERT to prevent drift.

### Pair-validity `.refine()` defense — Zod-import-shared matrix at Layer 1 (no DB CHECK)

The candidate row's `(linked_entity_type, link_role)` pair-validity is enforced via Zod `.refine()` on `DocumentRelationshipCandidateSchema`, importing `VALID_PAIRS` from chunk-5's `sourceDocumentLink.schema.ts`. Zero DB CHECK on the candidate row. Three reasons:

1. **The candidate row isn't a commit.** `source_document_links` is the committed materialization that downstream Phase 5 + Phase 7 consumers act on; the pair-validity matters at commit-time (DB CHECK on source_document_links per chunk-5 line 199-215). The candidate row is a proposal-time audit record; an invalid pair on a candidate row is a Subsystem 1 bug that produces a candidate Subsystem 2 + Tier 1 will never act on (the same `documentLinkService.create()` Layer 1 CHECK rejects it at commit time).
2. **Lockstep cost.** Duplicating the 13-cell CHECK on the candidate table means two CHECKs that must stay synchronized across ADR-0016 §3 amendments. This is exactly the substrate-decision-integrity hazard Phase 2.5 Commit B was unwinding for `wrong_entity_exception` / `manual_born_paid_workflow`.
3. **Zod-import-shared matrix is the canonical Layer 1 defense.** Subsystem 1's TypeScript output is parsed by `DocumentRelationshipCandidateSchema`, which imports `VALID_PAIRS` from chunk-5. One matrix, two consumers (chunk-5 `CreateSourceDocumentLinkInputSchema.refine()` + chunk-1 `DocumentRelationshipCandidateSchema.refine()`), drift-resistant by construction.

`VALID_PAIRS` is currently `const` (not `export const`) in chunk-5's schema file — an export-status near-miss that chunk-1 widens as a co-located one-keyword modification in the bundled commit. Same precedent shape as chunk-6 broadening chunk-2's LEGAL_TRANSITIONS in the chunk-6 commit. Friction-journal entry codifies the near-miss + the matrix-defense-family export discipline for chunks 2+.

### TS-only closed vocabularies (no DB ENUM, no DB CHECK) — two at chunk 1

Per the persistence-on-row discriminator: closed vocabularies that persist on a row get full three-layer defense (DB ENUM + Zod + service emission per chunks-5-6 `linked_entity_type` / `link_role` / `exception_status` etc.). Closed vocabularies that live only at service-handoff boundaries — produced or consumed at service-layer interfaces without ever landing on a row — collapse to Zod-only defense.

Chunk-1 ships two TS-only closed vocabularies:

ADR-0018 §Schema-deltas explicit: "Trigger identifiers (T1–T10) are an algorithm-level vocabulary owned by this ADR, not a schema-level enum." Chunk-1 ratifies this — no `re_routing_trigger` DB ENUM type, no `_chunk_1_active` DB CHECK on trigger values, just `z.enum([...])` admitting 8 v1-active and rejecting reserved at Zod parse.

### Unknown document_type early-return — accept-and-return-empty

Per ADR-0018 §item 2 + ADR-0014 §7 Q65: `unknown` document type short-circuits to exception queue at the pipeline orchestrator level, before `completeCandidate` is invoked. If a caller invokes `completeCandidate(input)` with `input.document_type === 'unknown'` anyway, the service returns an empty candidate set (no matching performed) — caller routes to exception per Subsystem 2 branch (c). The empty-set return is the natural signal; no `ServiceError` is raised because the caller's mistake is recoverable by routing to exception (which is what the caller should have done anyway).

```typescript
if (parsed.document_type === 'unknown') {
  log.info({ document_case_id: parsed.document_case_id }, 'Subsystem 1 skipped for unknown document_type per ADR-0018 §item 2');
  return [];
}
```

Test category 3 verifies the contract (returns `[]`; no DB writes; no audit_log rows; info log emitted).

### Batch RPC + per-candidate audit_log + `'agent'` hardcoded `created_by`

`create_candidates_with_audit(p_candidates JSONB, p_audit JSONB) RETURNS UUID[]`. Batch shape (jsonb_array_elements iteration), parent-derived org_id per chunks 3+ canonical pattern, per-candidate audit_log row emission, `'agent'` hardcoded as `created_by` inside the RPC.

Three deliberate divergences from chunks-3-6 substrate-writer pattern (codified in friction-journal entry #19):

1. **Plural RPC naming (`create_candidates_with_audit`).** Chunks-3-6 RPCs are singular (`create_X_with_audit`, `enqueue_X_with_audit`). Chunk-1 is the first plural-naming instance because Subsystem 1 produces a set per ADR-0018 §item 2. Discriminator: batch-RPC shape → plural; singular-write RPCs stay singular.
2. **`'agent'` hardcoded inside RPC.** Chunks-3-6 pass `created_by` through from service (writer may be user or automation). Chunk-1 Subsystem 1 is automation-only at v1 (Router is agent-pipeline per ADR-0007 §Tier 2.5); substrate invariant enforced mechanically at RPC layer. Future chunks with always-automation writers hardcode at RPC; future chunks with user-or-automation writers pass through. Per-invocation `user_id` (when chunks-2+ ship Subsystem 3 with controller-initiated triggers like T10) captured separately in `audit_log.user_id`.
3. **Per-candidate audit_log row, NOT one summary row per RPC invocation.** N candidates → N audit_log rows in single transaction with same trace_id. Matches chunks-3-6 per-write semantic; preserves per-candidate forensic queryability ("show me the audit row for candidate X" via `entity_id`). Logic Receipt's pipeline_trace captures the invocation-level summary on the complementary surface (chunks 2+ when Subsystem 2 lands proposal envelopes per ADR-0007 Q30).

Audit action string `'document_relationship_candidate_created'` — 41 chars, the longest action string at chunks-1-6, but within range. Chunk-1 follows chunk-5's full-table-name convention (`source_document_link_created` from `source_document_links`) over chunk-6's semantic shortening (`exception_enqueued` from `exception_queue_entries`); the convention permits semantic shortening but doesn't mandate it. Entity type `'document_relationship_candidate'` — singular, dropping the table-plural -s per chunks-5-6 convention.

ADR-0018 §Schema-deltas reads "ADR-0018 introduces no new platform tables and no new source-document schema columns. It introduces one audit-event type: `router_re_evaluation_fired`." This refers to events with structured payloads + dedicated emission semantics (Subsystem 3 telemetry). Canonical `recordMutation` instances with chunk-introduced action strings are NOT new event types — they're instances of the existing universal pattern per ADR-0011 §1. Chunk-1 emits `'document_relationship_candidate_created'` per canonical pattern; not an ADR-0018 §Schema-deltas-named event.

- Subsystem 1 writes `document_relationship_candidates` rows.
- Subsystem 2 writes `document_cases.current_relationship_candidate_id`.

### Cross-ADR boundary with ADR-0014 §11 (pipeline → Router handoff)

ADR-0014 §11 specifies that the match-against-existing-state subsystem produces an "incomplete candidate" (concept-prose, lowercase) — the pipeline output that flows into the Relationship Router for completion. ADR-0014 §11 names the TypeScript type `DocumentRelationshipCandidate` (PascalCase) as the canonical handoff type, but does NOT codify field shape in §11 (chunk-1 invents the row shape per the DDL above) and does NOT name an `IncompleteCandidate` PascalCase type or a `requiresTransactionalLookup` boolean flag — those are concept-phrase ideas in prose, not codified TypeScript.

Chunk-1's `CompleteCandidateInputSchema` is the materialization of ADR-0014 §11's incomplete-candidate handoff payload. The schema name follows the chunks-5-6 `<Verb><Entity>InputSchema` naming convention (method-verb + entity-noun): `documentRouterService.completeCandidate()` → `CompleteCandidateInputSchema`. Phase 7 pipeline (when it ships) produces this shape per ADR-0014 §11; the schema is forward-compatible.
